# #37 — durable evidence, migration and retention

Research date: 2026-10-16. Scope is issue #37 under #22; dependencies #34/#35. No model runs or live crawl. This report separates documented evidence from proposed engineering choices. Source pages and papers were opened and checked, not inferred from search snippets.

## Findings from this repository

- `monitor/snapshot.py` currently serializes products with `asdict`. The `evidence_contract` attachment deliberately is **not a dataclass field**, so existing snapshot writes silently omit the entire captured trust graph. Persist attachments explicitly before/alongside product JSON; adding a table alone does not repair this.
- `TrustContract.to_dict()/from_dict()` already preserve Decimal and aware UTC using typed tags, including mappings containing `$type`. Reuse that codec for trust metadata. The legacy snapshot encoder emits Decimal strings and timestamp strings; retain its old product JSON compatibility rather than replacing the whole historical format.
- Product contracts contain nested `/variants/N/...` observations; standalone variants also have attachments with relative paths. Define one authoritative owner per persisted contract and preserve both views without accidentally treating equal observation IDs with different field paths as global records.
- `Evidence` requires an excerpt or a resolving retained-data pointer. An expired payload cannot be reconstructed as an ordinary `Evidence` with a missing fragment. Retrieval must return an availability envelope/tombstone, and effective trust inspection must account for it.
- Existing identity migration and `created_at`, completeness/scope metadata must remain intact. Migration must not fabricate capture timestamps from snapshot creation or migration time.

## Primary evidence and implications

1. Buneman, Khanna and Tan, **Why and Where: A Characterization of Data Provenance** (ICDT 2001): distinguishes data influencing a result from the source locations from which values were obtained. It models paths identifying source locations. This supports retaining both observation-to-evidence links and exact pointer/fragment provenance. It does not establish source truth or confidence. [Author institution PDF](https://www.pure.ed.ac.uk/ws/files/16509989/Why_and_Where_A_Characterization_of_Data_Provenance.pdf).
2. Green, Karvounarakis and Tannen, **Provenance Semirings** (PODS 2007): annotations track dependencies of relational results on source tuples. Engineering implication: retain all contributing reference edges, including composite/aggregate inputs; deduplicated bytes cannot replace dependency identity. A semiring engine is unnecessary for this MVP. [Author PDF](https://www.cs.ucdavis.edu/~green/papers/pods07.pdf).
3. SQLite **Atomic Commit** documents all-or-none changes in one transaction, including crash recovery under its stated filesystem assumptions. Engineering implication: put snapshots, contract owners, evidence, payloads and reference edges in the **same database transaction**; do not split payloads into uncoordinated filesystem writes. Do not disable journaling/synchronization for speed. [Official documentation](https://www.sqlite.org/atomiccommit.html).
4. SQLite **Foreign Key Support** requires enabling FK enforcement separately per connection and notes changing it within a transaction has no effect. Engineering implication: `PRAGMA foreign_keys=ON` immediately after connecting; use real constraints and child-key indexes, not application validation alone. [Official documentation](https://www.sqlite.org/foreignkeys.html).
5. SQLite **Transactions** documents one writer and `BEGIN IMMEDIATE` acquiring a write transaction or failing busy. Engineering implication: extract/validate/encode outside the write lock, use a bounded busy timeout, then one short write transaction; explicitly roll back exceptions. Do not retry indefinitely. [Official documentation](https://www.sqlite.org/lang_transaction.html).
6. SQLite **ALTER TABLE** documents supported additive changes and the general rebuild procedure. Engineering implication: additive side tables plus nullable metadata minimize disruption; schema migration is versioned, transactional and restartable. Never directly edit `sqlite_schema`. [Official documentation](https://www.sqlite.org/lang_altertable.html).
7. SQLite **PRAGMA** documents application-owned `user_version`; `integrity_check` does not replace `foreign_key_check`. Engineering implication: version migrations explicitly, reject unknown newer schemas, and test both structural integrity and graph referential integrity. [Official documentation](https://www.sqlite.org/pragma.html).

## Proposed implementation contract (engineering choices)

Public API names are proposals for skeleton owners to settle consistently with #38:

- `get_evidence(evidence_id, *, db_path=...) -> EvidenceLookup`: result has `status` (`available`, `expired`, `missing`, `unsupported`), reason, optional validated `Evidence`, optional expiration time. `missing` means no such ID; `unsupported` describes known legacy owners with no captured graph, not an invented legacy evidence ID. For corruption/version errors raise a distinct error; never return available on malformed payloads.
- `load_snapshot(snapshot_id, *, db_path=...)`: supplies owner records and trust graphs/effective trust metadata. Raw historical observation state remains auditable; effective view must not expose trusted values after required evidence expires.
- `prune_evidence(*, db_path=..., before=None, dry_run=True, batch_size=...) -> PruneReport`: explicit, bounded operation with counts, protected refs and reasons; default expiration policy protects references retained by snapshots. Optional explicit expire-referenced mode must atomically tombstone payloads and make every affected effective observation unavailable.
- Keep `snapshot(...) -> int` backward compatible; capture attached contracts before serialization. Use internal `persist_snapshot(conn, products, metadata, contracts)` sharing the caller transaction. Revalidate contracts at the persistence boundary.

Schema sketch: keep `snapshots` unchanged except optional evidence-version/status marker; add `evidence_contracts(snapshot_id, owner_key, schema_version, contract_json)` with unique owner per snapshot, FK to snapshots; `evidence_records(evidence_id PRIMARY KEY, schema_version, metadata_json, payload_hash, status, reason, expired_at)`; `evidence_payloads(payload_hash PRIMARY KEY, encoded_payload, byte_size)`; `evidence_references(snapshot_id, owner_key, observation_id, evidence_id)` with compound owner FK and evidence FK. Owner key includes product position or stable owner discriminator plus variant position where applicable; do not assume variant observation IDs are globally unique across derived views. Store all resolutions/alternatives in contract JSON, and index reference evidence IDs for retention. A simpler contract-per-owner store is acceptable if reference edges remain queryable and validated.

ID scope: existing IDs are canonical UUIDs, currently unique within a contract. Promote persistent evidence IDs to DB-wide immutable identities: exact repeat is idempotent; same ID with differing metadata or bytes is an explicit conflict, never overwrite. For observations use `(snapshot_id, owner_key, observation_id)` identity. Cross-database portability remains #38. Byte dedup uses a SHA-256 of canonical **typed encoded** fragment bytes; URL/time/role/pointer remain separate per evidence capture, so equal fragments captured at different times are not the same provenance. Verify payload bytes on retrieval; a hash proves stored-byte consistency, not authenticity or correctness.

Retention defaults: no automatic deletion; explicit prune with dry-run and protection of referenced evidence. This favors historical correctness and must document that total DB size can grow. Preserve existing capture caps (4096 UTF-8 bytes per fragment and 65536 per product) and enforce a documented serialized contract/snapshot cap before entering the transaction. Choose one cap with tests rather than implying these capture caps bound total database growth. Expired IDs retain small tombstones while references exist; deleting shared bytes only occurs after **all** available evidence records using the hash have been expired/deleted. Never silently recapture an expired ID or mark its old observation fresh.

Migration: serialize upgrades under `BEGIN IMMEDIATE`; inspect existing columns/version, create additive tables, mark historical owners unsupported with a stable reason, preserve original JSON and identity/history. Record schema version only at successful commit. Running twice changes nothing. For an existing snapshot that already lacks attached contracts, do not infer support from product scalars, `raw_data`, timestamps or provenance-looking keys. If explicit serialized trust data is already present, only import after strict validation and without rewriting observed times.

## Failure cases and acceptance gate

1. Restart a file-backed database in a new connection: product/nested variant and standalone variant references resolve original URL, pointer, fragment, time, Decimal and mapping-tag values.
2. Inject failure after snapshot insert and after evidence/reference writes: reopen and assert no partial snapshot, alias/identity mutation or unowned available evidence survived.
3. Migrate legacy DB twice: row IDs, product/variant IDs, prices, timestamps, completeness metadata and unsupported reasons unchanged; old naive `created_at` stays historical metadata, never becomes observed_at.
4. Two snapshots share a fragment and/or evidence ID: default prune protects retained refs. Explicit expiration produces tombstones plus unavailable effective support across every owner; no observed trusted values survive required-fragment loss. One expired evidence must not remove bytes used by another available record.
5. Same evidence ID/different content fails atomically. Malformed pointer, unsupported schema, invalid UTC/nonfinite Decimal and oversized contracts fail before persistence.
6. Test bounded contention and rollback; test missing/expired/unsupported/corrupt outcomes independently. `PRAGMA integrity_check` is `ok`, `PRAGMA foreign_key_check` returns no rows.
7. Run targeted monitor, identity, completeness, contract, capture and resolution regressions with `PYTHONPATH=src`; fixtures are offline. Do not add unrelated local-model or broad performance sweeps.
