# Portable evidence bundles: #38 research

Research date: 2026-10-16. Scope: FR-05/FR-06, dependent on #35/#36/#37. Read issue #38, current evidence contract/data model, `_models.py`, `_evidence.py`, export writers and export API. No model runs or code changes.

## Findings grounded in primary sources

1. [W3C PROV-DM, especially bundles and derivations](https://www.w3.org/TR/prov-dm/) describes provenance as records of entities, activities and responsibility; named bundles can carry provenance about provenance. **Application inference:** preserve captures, observations, alternatives and policy rationale together. A selected scalar alone cannot reproduce the decision. This ticket does not require claiming PROV conformance or adding an RDF dependency.
2. [RO-Crate research paper, Packaging research artefacts with RO-Crate](https://www.researchobject.org/2021-packaging-research-artefacts-with-ro-crate/manuscript.html) proposes lightweight packaging of data with machine-readable contextual metadata. **Application inference:** a small versioned JSON envelope carrying Product/Variant values plus contracts meets this application's offline inspectability need. Full JSON-LD/RO-Crate packaging is unnecessary for the acceptance scenarios.
3. [RFC 8259](https://www.rfc-editor.org/info/rfc8259/) defines JSON's limited native types, excludes nonfinite numbers, warns that duplicate object names yield unpredictable consumer behavior, and allows parser resource limits. **Application inference:** use the existing tagged codec for Decimal and UTC datetime; reject duplicate JSON keys, malformed tags, nonfinite values and unreasonable input sizes on bundle loading. Do not silently coerce unsupported Python values.
4. [RFC 8785](https://www.rfc-editor.org/info/rfc8785/) defines deterministic JSON canonicalization for hashing and constrains numbers to IEEE-754 doubles. **Application inference:** arbitrary Decimal prices belong in tagged strings; ordinary Python `sort_keys=True` must not be advertised as RFC 8785 compliance. A bundle need not implement cryptographic canonicalization to preserve existing evidence UUIDs. Use an explicitly documented local serialization if hashing row identity.
5. [RFC 3339](https://www.rfc-editor.org/info/rfc3339/) provides interoperable timestamp syntax and UTC/offset semantics. **Application inference:** require timezone-aware UTC timestamps, preserve microseconds and use one documented UTC spelling on write; reject naive/invalid datetimes. Current evidence codec already requires UTC on encode.
6. [RFC 6901](https://www.rfc-editor.org/info/rfc6901/) defines JSON Pointer escaping and resolution/error behavior. **Application inference:** validate retained-data pointers after load, including root `""`, `~0`, `~1`, arrays and unavailable targets. A remote source URL is context, not locally retrievable evidence.
7. [RFC 8493, BagIt](https://www.rfc-editor.org/info/rfc8493/) separates payloads and manifests and validates payload checksums. **Application inference:** a sidecar should bind itself to the actual exported feed bytes with a SHA-256 digest plus format and explicit row mappings. A checksum detects mismatched files; it does not authenticate publisher, prove capture truth or establish validated confidence. No full BagIt implementation is needed.

## Recommended application contract (engineering inference)

Reuse `encode_value`/`decode_value` and `TrustContract.to_dict/from_dict` from `_evidence.py`. Add a small portable module, preferably `_portable.py`, shared by export and SQLite. Keep the transport bundle version separate from `TrustContract.schema_version`.

Suggested envelope: `bundle_type`, `schema_version=1`, `records`. Each record contains a stable `record_key`, typed Product data, optional product trust contract and explicit index-aligned variant contracts. Restore Product.platform as Platform and each nested variant as Variant; then attach `evidence_contract` on Product/Variant exactly as normalization does. Dataclass `asdict` alone loses these dynamically attached contracts. Do not manufacture capture timestamps or IDs for legacy products: missing contracts continue to produce unsupported trust views.

Encode values once: contracts already return tagged JSON-safe maps. Passing that serialized contract through `encode_value` again escapes the codec's own tags and breaks decoding. Build an envelope from separately encoded product values and existing contract dictionaries, then deserialize those branches separately. Preserve list order, Decimal exponent/trailing-zero representation through `str(Decimal)`, UTC instants/microseconds, IDs, reasons, transformations, raw scores, score kinds and validated-confidence metadata. Preserve literal user maps containing `$type` using the existing mapping escape. Document tuples/sets/bytes/arbitrary objects as unsupported rather than claiming arbitrary Python-object losslessness.

Strict loading sequence: parse with duplicate-key/nonfinite rejection; check exact supported envelope/version and required container types; check unique record keys; validate typed values; reject unknown Product/Variant fields and invalid Platform; reconstruct model types; reconstruct all contracts through their current validators; verify variant-contract count/alignment; verify contract references, same-field selections and retained evidence pointers. Contract ID scope is local to each contract, so report lookups must include record key and product/variant scope. Reject corrupt records with actionable errors rather than dropping provenance or replacing it with unsupported state. Unsupported and expired are valid recorded states, not parse failures. Do not refresh evidence or rerun resolution during import.

## Feed compatibility and mapping

Keep current `to_json`, `to_csv`, `to_feed` defaults and file schemas compatible. Offer explicit portable export/load APIs and optional companion path on CSV/feed export. Export sidecar from Product objects before reducing to plain dicts. Stable keys should use existing canonical identity when unique and scoped (supplier + canonical product ID), with deterministic fallback identity for unkeyed records. Reject or explicitly disambiguate collisions: external_id, title, URL and row index alone are not globally unique. Document fallback stability limits; a content-derived fallback can change when the record changes.

Keep feed rows untouched. A sidecar mapping can hold `{row_index, record_key, format-specific-id}` and the exact feed digest. Row index locates a row within that verified immutable export; record key identifies its bundle record. Verify digest before trusting the map. Duplicate marketplace IDs must not silently overwrite mappings. Preserve all variant contracts even when feed projection emits only product rows. If a consumer edits/reorders the file, it must rebuild/verify mappings; do not imply that original row indices remain valid.

## Offline acceptance fixtures

- Golden conflicting Product with observed selected candidate, retained alternative, unknown/unsupported/expired fields, nested variants, Decimal `1.2300`, UTC microseconds and literal `$type` maps. Compare values/types and all contract dictionaries after independent JSON load.
- Empty catalog, legacy Product with no contract, duplicate identities/IDs, dangling evidence, invalid selected observations, unknown versions/tags, malformed enums, nonfinite values and timezone-naive datetime rejection.
- Feed and CSV default-byte/schema regressions; opt-in sidecar resolves every row, flags wrong digest, preserves duplicate-ID rows and references retrievable field evidence.
- Reuse the same portable record representation in SQLite; never let persistence invent a second Decimal/datetime/contract codec.

## Integration boundaries / limits

Local excerpts or retained fragments travel; remote-only context does not become archived content. Existing 4 KiB fragment and 64 KiB product capture caps remain documented. Expired evidence stays expired; imported policy output is historical, not newly validated. Integrity checking cannot establish capture authenticity. Paper/standards support provenance preservation and interoperable representation; specific Python API names, hashing rules and envelope choices above are implementation recommendations, not externally mandated designs.
