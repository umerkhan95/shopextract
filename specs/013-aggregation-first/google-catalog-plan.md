# Complete Google category catalog integration plan

Author: /root/google_catalog_plan. Date: 2026-10-31. Planning only; proposed interfaces below are not implemented or approved runtime contracts. The user's expanded scope makes the **complete pinned Google catalog** the common target for new aggregation workflows. Missing product classification remains valid; missing integration coverage for a valid pinned category is a defect, not an optional future category pack.

## Required result and denominators

- Import every category ID/path and parent relation from one pinned official English resource, including all internal and leaf nodes. The session's observed public file contains5,595 category rows and header2021-09-21; actual implementation must acquire permitted bytes, save SHA256 and recount. Do not hard-code a supposedly permanent count or infer an October2026 upstream release.
- Every pinned Google ID must resolve, be selectable as a mapping target, bind to a native categorized record and survive aggregation/export/reload. Google coverage completion is `integrated valid target IDs / pinned valid target IDs = 100%`, plus independent structural/path tests. Report nodes, roots, leaves, edges, errors and exclusions separately; no supported catalog node may be excluded to obtain100%.
- Catalog integration is not universal merchant classification: unrelated store categories may remain unmapped/ambiguous, and catalog labels never provide product specifications or authorize same-product grouping. All5,595 observed Google nodes are in the planned catalog scope; no per-leaf comparison profile is required.
- Initial locale is complete `en-US`, not all languages. Preserve source locale; optional other locales require their own exact resource/hash and proven ID correspondence, never translated-label matching. Shopify14,606-node catalog remains separately namespaced and compatible.

## Proposed module, API and command surface

New `taxonomies/google/` owns TXT source contract/parser, catalog validation/indexes, pin/manifest, preparation/publication and offline loader. Proposed namespace `google:product_category` matches the native captured declaration; target registry version must combine upstream header, locale and immutable digest. An unknown observed source version stays unknown even when target catalog identity is known.

Proposed Python surface: `load_google_taxonomy(version, *, locale='en-US', catalog_root=None, fingerprint=None)`; read-only `category(id)`, `resolve_path(full_path)`, `ancestors(id)`, `children(id)`, bounded `iter_categories(cursor, limit)`; `google_taxonomy_options(scope, *, category_ids, mappings, allow_unknown_source_version=False, taxonomy)`; explicit normalization/aggregation wrappers that observe once, select relevant IDs and reuse native mapper/binder. Exact signatures/errors are child G2 work after behavior/red tests.

Proposed CLI operations under a new `taxonomy google` group: `info`, `lookup ID`, `resolve-path PATH`, `list --cursor --limit`, `validate`, explicit `prepare --source FILE --catalog-root PATH` and `update --source FILE`. Mapping/aggregation commands explicitly select Google target catalog; existing Shopify/default extraction commands stay unchanged. No model, browser, download or update runs during import/help/lookup. The new aggregation configuration defaults to the pinned Google target when provisioned; no Google category is required for product admission.

Catalog parser treats IDs as namespace-scoped decimal strings, retains original full paths, and constructs parents only from validated catalog path prefixes. Reject duplicate IDs, duplicate full paths, absent parent paths, cycles, empty labels/segments, malformed header/UTF-8, duplicate/BOM ambiguity and unsupported source versions/shapes rather than guess. G2 must distinguish malformed input from unknown lookup and ambiguous installation, and define exact canonical comparison/whitespace policy without relabeling source data. Known removed IDs remain resolvable under retained historical catalogs; no replacement is inferred.

## Acquisition, packaging and update contract

1. Source task reviews official use/redistribution terms, records URL/locale/header/source SHA256/acquired time/terms receipt and selects supported route. Repository MIT and Shopify MIT do not license Google's dataset. This is an explicit resource distribution prerequisite, not a request for user permission or a block on unrelated offline engine work.
2. Preferred route, if supported by reviewed terms: preprepare the full verified Google resource with notices/provenance, include it in wheel and sdist, and prove offline installed lookup for every ID. Alternative supported route: distribute code/schema and require an explicit operator-supplied complete official artifact prepared locally; installation/help remain functional and missing resource yields an actionable error. This alternative still must load and verify **all** IDs; do not describe a resource-unprovisioned install as full taxonomy ready.
3. Separate resource limits from1MiB CLI product input: proposed official source UTF-8 limit2MiB, generated decoded catalog8MiB, one manifest64KiB, one sequential build, RSS512MiB, total resource operation120s; initial three-node smoke saved before full sweep. Pin actual sizes, compression expansion and hashes before G2; if exceeded stop and review the design, never silently lift limits.
4. Resource identity is namespace/header/locale/source digest plus generated-format version/digest. A mutable `latest` name never identifies persisted records. Manifest stores exact node/root/leaf/edge counts. Lookup validates resource integrity even on cached reuse, and preserves immutable catalog instances. Loading does not fetch or refresh observed product timestamps.
5. Update stages complete new bytes/indexes, validates everything, then publishes atomically as a new immutable directory. Keep previous identity available; an optional default pointer changes only after successful validation. Write/interruption/digest/schema failures preserve previous pointer/catalog. Historical reads request exact identity; mismatched/retired targets remain visible instead of being remapped.

## Required full-catalog verification

- First three-reference smoke chooses actual pinned root, internal and leaf IDs from different branches, not hard-coded laptop/boot/fridge specialization. Then visit every pinned ID once in deterministic order through actual native mapping and companion encode/decode, with generated Google feed source captures explicitly labelled controlled/synthetic. For each ID assert exact target, namespace/version/digest, source pointer/support, original ID/path, ancestors and aggregation classification after reload. Isolated valid targets use finite options; no5595-target job.
- For every node assert lookup-by-ID and complete-path agree; every nonroot has exactly one validated parent, parent/child edges reciprocate and all reachable nodes/leaf/root counts reconcile. Test all root branches and maximum actual depth. If official source violates native ancestry8, retain catalog but expose explicit affected-operation limit; do not falsely count failed binding as integrated100%.
- Distinct negative cases: duplicate ID/path, missing parent, malformed Unicode/header, truncated source, ID/path mismatch, wrong locale/version/digest, unknown/retired ID, two installed same-header catalogs without fingerprint, malicious path traversal/symlink selection, corrupt cache hit and publication interruption. Full known ID coverage does not replace these risks.
- Exercise selected-target/rule limits999/1000/1001 and config bytes below/at/above256KiB; catalog listing pagination must cover all IDs once with revision-bound cursors and no duplicates/omissions. Same target full-path/ID alternatives converge; source versions remain unasserted. CLI1MiB output growth rejects or uses declared pages, never truncates.
- Begin exhaustive driver with a measured three-ID smoke, then one sequential whole-catalog run within proposed180s/512MiB and saved per-batch progress; related semantic cases are separate. Stop on failure; record minimal case and one diagnosed repair. Do not increase repository240s/480s test ceilings. Installed wheel sweep may reuse the same canonical test inventory without claiming every category was observed at merchants.
