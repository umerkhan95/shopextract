# Full Google target coverage and source mapping implementation design

Planning amendment: 2026-10-31. Author: `/root/google_mapping_plan`. No implementation, runtime verdict, source corpus download or GitHub mutation. This design expands the earlier optional-category roadmap: **every node in the pinned Google taxonomy must be a supported ShopExtract target**, while products with missing source classification remain usable. Proposed interfaces below must pass child G1/G2 before code.

## Meaning of complete mapping

The required target denominator is the exact set of IDs parsed from a pinned official Google resource, including parents and leaves. The current observed English file has5,595 nodes; source acquisition must recount rather than hardcode that number forever. Completion requires100% of pinned IDs to resolve, accept an exact supported declaration, traverse the actual category mapper/binder/strict codec, and remain available to aggregate reports/API/CLI. No category-specific Product schema, profile or handwritten identity rule is required.

Source crosswalk coverage has a different denominator. A merchant's opaque Woo category7 is not Google category7, and14,606 Shopify nodes cannot be assumed to correspond one-to-one to Google nodes. The deliverable includes exhaustive target coverage plus an explicit source-mapping ledger; unsupported source mappings remain unresolved instead of invented. A Google catalog node's existence proves neither a merchant assignment nor product specifications.

## Resolution layers and decision contract

1. **Direct observed Google declaration:** validate captured exact ID or full path against the explicit pinned catalog/locale. An unambiguous supported declaration maps to that target. No leaf-only restriction: every official parent is also a valid target. Unknown/retired ID, unknown path, unsupported capture or version mismatch stays explicit. Preserve source versionNone; trusted resolution against a pinned target does not retroactively establish merchant source version.
2. **Official crosswalk:** coordinator inspected the [pinned integration README](https://github.com/Shopify/product-taxonomy/blob/2e9aa2e9b882383952c63d212add13eb80f46cf9/data/integrations/README.md) and directory at Shopify2026-08 commit2e9aa2e9b882383952c63d212add13eb80f46cf9. Google2021-09-21 has `data/integrations/google/2021-09-21/mappings/from_shopify.yml`,1,355,910bytes, Git blob2a57f754fd66a6c09010fac5ca1b93d45be5f629; reverse `to_shopify.yml` was absent from that directory. Inspect/import this actual forward resource as a required task; no lossy auto-inversion. README names release asset `integrations.all_mappings.en.json.gz` and notes source `unmapped_product_category_ids` are excluded from generated distributions, so inspect source exclusions independently. Full bytes/rows/counts/semantics are not yet fetched. Audit license/terms and exact endpoint compatibility; use pinned source or versioned assets, not retired dist output. Pin source Shopify digest, target Google digest and mapping digest together. Every row has validated endpoints, relation precision, direction and provenance; dangling rows are quarantined and counted for diagnosis and prevent publication of the invalid crosswalk; no invalid partial mapping index is activated.
3. **Explicit merchant mapping:** trusted declarative selectors bind exact merchant namespace+store/catalog/channel/locale scope and a captured ID/path/label to Google IDs. Rules carry version and audit provenance. Different stores with identical IDs/labels remain distinct; no automatic source-label equality with a Google leaf. Existing support/partial state remains authoritative.
4. **Unresolved/proposals:** no sufficient mapping returns unmapped/unavailable; conflicting eligible routes or multiple effective targets return ambiguous. Optional future search/classifier suggestions live in a separately typed proposal collection, never `mapped` facts or source evidence. No model/classifier is needed for the initial complete-target integration.

Route order describes capability, not silent precedence. Preserve all route decisions. A supported direct declaration and contradictory trusted crosswalk must yield an effective classification conflict unless an explicit versioned override policy is supplied; no arbitrary first/last result. `MappingDecision.mapped` can currently contain multiple target_ids, so the new effective-Google projection must require exactly one distinct compatible target before presenting a single category. Many-to-many crosswalk rows retain all candidates; neither metadata ancestry nor parent/child co-membership automatically resolves the choice. A known broader-only relation may be shown as such, never claimed an exact leaf. Default new aggregation uses Google targets while legacy Shopify APIs/default formats stay unchanged.

## Full catalogs with existing finite job limits

Load the full Google catalog/crosswalk into immutable indexed lookup resources, separate from Product/jobs. Resolve only observed source keys and referenced target candidates for a record/batch. Build a deterministic relevant CategoryOptions subset with at most1,000 targets/1,000 rules,100 terms,200relation refs and256KiB config/companion ceilings; lower limits win. Identity rules are generated for requested exact ID/path declarations, not authored manually5,595times. Crosswalk indexes are lookup data, not5,595rules embedded in every job.

If one request exceeds limits, return explicit partial/rejected status with reasons and use an external paged/batched catalog sweep; do not silently drop candidates or raise limits. Every batch records its pinned catalog/policy and original source facts. Per-product convenience configs can differ; do not misrepresent them as one persisted job policy. Catalog-wide enumeration/API pages are separate finite resource operations; immutable revision-bound cursors prevent mixing releases.

Locale belongs to the pinned path index and mapping context. Same Google ID with translated labels is one ID only after the actual resources establish correspondence; no string translation at runtime. Unknown locale/path remains unresolved. Retired IDs retain their historical catalog; a later lookup does not redirect them to a convenient ancestor. Crosswalk updates create explicit new classification revisions; existing reports/snapshots remain reproducible.

## Canonical source-ledger partition

For each known source ID in pinned S, apply this ordered partition: (1) incompatible/unavailable source-target version pair gives `version-unavailable`; (2) a dangling endpoint or contradictory rule/exclusion involving that source gives `invalid-reference` and prevents crosswalk publication; (3) validated rows with one distinct target give `mapped-single`, with multiple distinct targets `mapped-multiple`; (4) no row plus an explicit upstream exclusion gives `explicit-upstream-unmapped`; (5) otherwise `missing-rule`. Identical duplicate rows may be deduplicated with retained row diagnostics; counts remain per source ID. A row whose source ID is outside S is a separate invalid-row diagnostic and also blocks publication, never a phantom member of S. Unsupported merchant capture, exact/broader precision and effective-route ambiguity are secondary axes; they do not rename or double-count the official source partition. The six primary counts sum exactly to |S| in diagnostic reports; an invalid index never becomes active merely because its ledger reconciles.
