# Aggregation-first product information and comparison

Planning date: 2026-10-31. Authors: aggregation_planner and coordinator. Scope amendment: user explicitly requires the COMPLETE Google category catalog and mapping integration, using multiple agents. This supersedes the earlier lookup-only/resource-optional interpretation. Runtime implementation, publication and GitHub changes are outside this planning task.

## Outcomes and requirements

Build a shared aggregation pipeline: captured supplier products and variants → reusable normalized records → reviewable identity groups and offers → source-backed specifications and comparison. Google categories organize the aggregation; they do not determine product identity or prescribe a separate implementation for each category. Richer information means measured supported-field availability, traceable differences and freshness, not an unverified claim to outperform Google's private systems.

FR01 **Preserve main and separate proposed work.** Baseline main is a900599. It already includes the full pinned Shopify taxonomy (14,606 category nodes, 26 roots), category mapping, supplier-scoped identities, pair matching and evidence transport. Keep that catalog and historical records. Refrigerator-specific implementation belongs to unmerged draft PR98, head90d5bd1; neither merge nor delete it implicitly. Produce a file/contract-level keep/adapt/defer disposition before implementation. Do not widen existing Product/Variant.attributes, require refrigerator flags, or change legacy profile definitions through this project. Old specs remain historical; link a new supersession decision rather than rewriting their results.

FR02 **Complete versioned Google category layer.** Integrate EVERY category ID/path in a pinned official Google Product Taxonomy catalog as an addressable mapping target, including parents and leaves. Google is the default target namespace for the new explicit aggregation workflow; legacy extraction/Shopify defaults stay compatible. Catalog identity includes source URL, upstream version, locale, acquired time and content digest. Public English file observed in this session reports version2021-09-21 and5,595 nodes including parents; these are not leaf counts or evidence of an October2026 release. Recount pinned bytes and validate uniqueness, paths, parents and root/leaf denominators. Review source use/redistribution terms before distribution; Google's data does not inherit MIT from our code or Shopify. An operator-supplied validated COMPLETE artifact is the fallback resource route with actionable setup, never a partial sample. Full-catalog integration is mandatory for overall completion under either route. Runtime lookup makes no taxonomy download. Failed updates retain the last valid catalog; historical version/digest stays loadable. Retired/unknown IDs are explicit, never silently reassigned.

FR03 **Preserve source classification separately.** Retain merchant/Shopify/feed observations, original namespace/version/locale/scope, label/path and support independently of Google assignments. A feed-declared Google ID or complete path resolves exactly under a specified catalog; unknown source version remains unknown. Trusted declarative crosswalks are versioned mapping decisions, possibly absent, ambiguous or many-to-many, not merchant facts. Preserve all candidates; choose at most one effective Google classification for a projection only when the exact mapping is unambiguous under explicit policy. No automatic label equality, category position, ancestor inheritance or arbitrary first-candidate selection. Unclassified products remain usable in aggregation and comparison. Categories never supply product specifications or authorize identity.

FR04 **Additive shared product/offer/specification contract.** Introduce an explicit versioned opt-in aggregate companion/projection referencing native portable Product/Variant records and their evidence contracts. Keep Product/Variant constructors, `attributes: dict[str,str]`, supplier canonical IDs, existing extraction/compare defaults, snapshots and feed/export formats unchanged. Rich specification values belong to this companion, with source owner/path, original label/value, semantic key when known, normalized value/unit when supported, transformation rule/version, locale, captured observation time and evidence references. Unknown fields/units remain retained source data. Literal reserved-looking keys, Unicode, missing/null/empty/zero/false, exact Decimal spelling and nested variant ownership must roundtrip. Do not copy an unsupported compatibility scalar into a trusted aggregate fact. Define the actual wire/API schema at G2, before implementing it.

FR05 **Identity grouping preserves supplier records.** Reuse reviewed native identifier/matching primitives through a new explicit opt-in identity projection; add a bounded deterministic grouping layer rather than treating one-to-one catalog matching as an existing many-store aggregator. A global group reference never replaces supplier canonical identity or rewrites history. Every grouped record has an accepted identity decision and inspectable supporting source observations; format-valid GTIN alone does not establish captured support. The legacy matcher treats any asymmetric attribute as missing and any unequal attribute as conflicting: do not pass arbitrary richer specifications wholesale to it or alter its defaults. The new projection separates captured identifiers, explicit variant options, pack/bundle/condition and approved identity-sensitive cues from descriptive specifications. A missing descriptive specification alone cannot veto an otherwise supported identity; unresolved explicit distinguishing dimensions remain review-only. Unknown semantics are retained without guessing they are descriptive or inventing a category policy. Freeze the exact admission rules and negative cases at G2; captured strong identifiers still require absence of known identity conflicts. Title/category similarity alone produces candidates. Conflicting brand/MPN/GTIN, variants, pack/bundle quantities and relevant distinguishing attributes veto unsafe grouping. Unknown distinctions remain reviewable. When A–B and B–C appear exact but A–C conflicts, do not merge the transitive component: retain a reviewable conflict set, without arbitrary record-order selection. Duplicate and reordered inputs produce the same decisions/group references for the same complete member set and pinned policy; incremental membership changes create a new group revision with explicit predecessor/member links. Do not promise a universal permanent product ID from imperfect inputs. Proposed initial admission ceilings are10,000 candidate/conflict relation evaluations and100 members per group, with deterministic supported-identifier blocking and no unconditional all-pairs scan across all inputs. Admission and exhaustion order must be canonical: an incompletely checked candidate component remains partial/review-only, never partly merged on arrival order. Child G1/G2 must freeze accounting for retries and all-member checks; grouped records cannot bypass safety by consuming an uncounted relation budget. One-to-one uniqueness in legacy catalog matching must not prohibit a legitimate three-store group.

FR06 **Offers are scoped observations.** Associate each offer with its supplier/product or variant, URL, observation time, evidence and available price/currency/stock/condition/pack/channel/locale context. Replays of the same scoped observation do not duplicate offers; distinct sellers, variants and observations never collapse merely because URLs or GTINs agree. For each supplier/listing/variant/channel choose a current observation at an explicit as-of time using recorded freshness policy; retain prior observations. Equal-time disagreeing observations remain conflicts. Rank only observed finite nonnegative prices in separate observed-currency and compatible condition/pack/variant cohorts; observed zero is valid, missing zero/USD defaults are not. Unknown stock is not in-stock. Unknown condition is a separate unranked context, not assumed new. Refurbished/new may share a product-family view but cannot share a lowest-equivalent-offer ranking. No currency conversion or package-to-unit price assumptions. A missing source/catalog never confirms product removal.

FR07 **Flexible specifications with conservative reusable normalization.** Capture attributes through existing extraction/support seams and preserve source spelling; do not require a domain profile to admit or display an attribute. Reuse approved common scalar/unit handling when semantics and provenance are explicit, retaining source and transform trace. Same unit dimensions alone do not prove same meaning: net/gross/freezer volume, product/package length, RAM/storage and regional shoe sizes remain distinct or unknown without an approved semantic rule. Unknown localized units and arbitrary aliases are not guessed. Initial normalization scope is finite exact mass/length/volume conversions; no currency, GB/GiB, shoe-size or free-text semantic conversion. Such optional future rules are reusable capabilities, not mandatory per-category schemas. No inference/model launch is part of the initial pipeline.

FR08 **Two comparison views.** Same-product view shows grouped offers and eligible price differences. Cross-product specification view aligns only explicitly compatible semantic keys/units/variant scopes, returns equal/different/unknown/conflicting with source references and all alternatives, and never reclassifies distinct products as identical. Unknown attributes can be displayed under their original labels without being declared comparable. No blanket better-product/value-for-money recommendation. Conflicting supplier specifications are preserved under existing field-specific authority/freshness resolution, with no manufacturer authority inferred from domain or taxonomy. Comparison may operate with no Google assignment.

FR09 **Honest insights and cost context.** Report per-view explicit denominators: input records, successful/partial/failed sources, grouped/unmatched/review records, observed/missing/conflicting/expired fields and eligible versus excluded offers with reasons. Report available source-supported specifications against an explicitly selected field set or union of observed semantic keys, not every possible category specification. Never call configured rules executed coverage or all taxonomy nodes product coverage. Item-price insights label their basis. Shipping/landed totals remain unavailable unless shipping, tax inclusion, destination, quantity, currency and required charges are explicitly comparable and supported; no free-shipping, tax or missing-charge assumptions. Initial scope can expose missing total context without acquiring checkout quotes.

FR10 **Persistence, update and bounded public access.** Aggregate companion export/import and local persistence must retain native records/evidence, source category facts, mapping policy/catalog digest, grouping revisions, offer observations and normalization policy. Existing snapshot schema/reading stays compatible; choose an additive companion store rather than silently overwriting old rows. Import does not refresh source timestamps or evidence. Re-evaluation under a different catalog/group/unit policy requires an explicit new revision; old reports remain reproducible. Reuse strict codecs and atomic publication; malformed/dangling references, duplicate JSON keys, unsupported versions and failed persistence produce no partially published aggregate. Initial JSON API/CLI uses shared finite limits and pagination; optional exports require explicit companion binding rather than breaking legacy exports. No orphan handles after cancellation.

FR11 **Measure and deliver bounded slices.** Implement in independently reviewed slices: baseline/PR disposition and Google source contract; native-record companion plus flexible specification transport; deterministic identity groups and offers; opt-in comparisons/insights; persistence/API/CLI integration and multi-source verification. Each executable slice requires behavior/test design, G1, skeleton and intended red acceptance tests, G2, reusable components, G3, implementation, focused/full checks, bounded mechanisms/stress/live and independent final review. Use saved-source-first evidence and no inference. Start a controlled synthetic smoke before stress/live expansion. Distinguish planning, mechanism pass, actual observed source fields, blocked live seams and real-market accuracy; do not promise million-product throughput from bounded checks.

FR12 **Exhaustive target integration with bounded work.** Every pinned Google target traverses actual lookup, bounded per-job options, shared mapper, categorized portable bind/reload and explicit public projection/export. An exhaustive ledger identifies every target/outcome and pinned hashes; completion requires100% target-ID set equality and zero omitted/skipped checks. The full indexed catalog stays outside per-job payloads: preserve existing1000targets/rules,100terms,256KiB config/companion bounds and lower native limits. Select relevant mappings/target subsets; never generate manually maintained per-category profiles or place the entire registry in a job. Installed/offline resource loading, preparation, updates/rollback, and category-aware aggregate API/CLI with pagination are required. These prove target integration, not actual merchant/product coverage across all categories.

FR13 **Audited directional crosswalk and six-source coverage.** Inspect/import the pinned official Shopify→Google mapping with exact source/target versions, hashes, exclusions and direction; never invent or invert a reverse crosswalk. Audit each Shopify source category to mapped-single/mapped-multiple/explicit-upstream-unmapped/missing-rule/invalid-reference/version-unavailable with explicit denominators. Google targets lacking inbound Shopify rules remain fully addressable. Generic Google-feed ID/full path is an exact route; all six native adapter families use captured declarations plus applicable official or trusted merchant-scoped rules. Missing evidence/rules produce unmapped/ambiguous/unavailable, not invented universal source coverage. Freeze source/version/locale/conflict precedence before code. Controlled real capture→map→portable→aggregate integration covers six families; actual live coverage is separate. No per-category formatting or unreviewed automatic classification required.

## Boundaries and compatibility

No deletion of Shopify taxonomy, wholesale PR98 merge/cherry-pick, silent migration to rich attributes, Google taxonomy scrape at import, exhaustive category-policy packs, unreviewed inferred category crosswalk/classification, semantic model fallback, inferred product truth, merchant writes, review UI, hosted service/OAuth, checkout scraping or distributed search infrastructure. Existing maintenance profiles stay optional and unchanged. Initial target is a bounded local aggregate snapshot built from saved native portable inputs, with offers current/as-of from retained inputs and explicit member-set revisions. It is not a durable event platform or millions-of-products service. Opt-in source acquisition is a later slice after offline contracts work; Google availability is not required to admit unclassified products. No manual classification of every arbitrary attribute is needed to retain/display it: only an approved finite semantic capability may align it, while explicit captured variant/pack/model cues determine distinguishing constraints. Unresolved such cues remain review-only. Future UI/search/large-scale storage can consume the same versioned outputs after separately scoped design.
