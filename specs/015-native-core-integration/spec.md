# Production extraction integration amendment

Status: proposed; independent G1/G2/G3 reviews pending. Date: 2026-10-31.

The user asked why Shopextract fallbacks were not exercised by taxonomy verification. Existing version1 verification fetches directly and invokes private static parsers; it does not exercise the API → discovery → UnifiedCrawl → CSS → optional LLM orchestrator. This amendment introduces an explicit production pipeline source and preserves version1 static behavior.

## Observable requirements

- FP-FR1: Version2 profiles select source_kind `production` for every site. Verification invokes the actual top-level `shopextract.extract` orchestrator, never `extract_one`, a private static parser, or a copied fallback algorithm. Pass the declared platform/shop URL, max_urls=1, explicit browser-enabled ExecutionPolicy and no LLMBudget. The existing orchestrator decides which eligible fallback to attempt and stops when it finds sufficient data. There is no promise every tier runs after an earlier tier succeeds.
- FP-FR2: Preserve version1 static profiles and their existing eight HTTP request/response-byte/scope bounds. Version2 uses a different explicit closed limit shape: `invocations` (1..2), `products` (1..4), `seconds` (1..120), `output_bytes` (1..1048576). Version2 does not claim bounded network request counts, response bytes, redirect origins, or browser subresources; these are unavailable in the existing orchestrator. It limits pipeline starts, retained products, parent wall time and serialized worker output. max_urls=1 is not a network request limit.
- FP-FR3: Fresh platform network-policy denial skips before any production subprocess, preserving the policy digest/reason/time and not_run downstream stages. Never remove proxies, change routes, add domains or retry a denied site through another transport. Existing production/browser configured network behavior otherwise remains unchanged; this amendment does not add redirect or merchant scope guarantees to that pipeline. A changed network policy alone is not proof of permission for every redirected/subresource host.
- FP-FR4: Each pipeline runs in an owned subprocess group, with at most one pipeline/browser family active. The shared deadline includes extraction, CLI mapping/export and cleanup; reserve a fixed bounded cleanup allowance from the existing total, never extend120s. Enforce stdout/stderr limits while draining rather than checking after unbounded communicate. On success, error, timeout, cancellation or output overflow terminate/kill remaining owned descendants, reap them, and record cleanup success. Unsupported lifecycle supervision fails closed before launch. Do not install browsers, start model servers, use environment LLM keys, or leave children behind.
- FP-FR5: Retain actual bounded ExtractionResult.raw_products, including original _capture, for existing Google normalization and export commands. Do not fabricate categories, source URLs, observation times or browser evidence. Missing source category remains needs_review. Zero products means no mapping/export execution. Limit retained raw records before serialization and record truncation rather than imply complete catalog coverage.
- FP-FR6: Report execution path `production`, actual result tier, URLs attempted/succeeded, bounded errors, result completeness, process state and artifact hashes. Explicitly report LLM disabled (no configured LLMBudget), browser enabled but actual browser attempt unknown unless independently observed, and per-tier attempt states unknown rather than infer attempts from final tier. `usage.network_requests` and `usage.network_bytes` are null/unobserved for production; `usage.pipeline_invocations` is exact. No fabricated HTTP status or fetched source byte hash where the pipeline did not expose them.
- FP-FR7: Existing pass requires mapped classifications and verified export. A production extraction success alone is insufficient. Controlled boundary runs always mode controlled/live_verified false. Policy denial, a missing browser required by the attempted source path, timeout and child error cannot yield pass. A sufficient API result may pass without launching or preflighting a browser. Actual browser startup or merchant extraction remains unverified when no live browser ran.

Non-goals: redesign every extractor network transport; enable paid/local inference; force retries after success; change platform detection, normalizer, category binder, Google catalog, existing public extract API or version1 behavior. The original full5595 and native Codex/live access blockers remain historical unmet gates.

## Slice A: category and CLI production integration

- NC-FR1: Add explicit `source_mode='native'|'production'` to extract_with_categories; legacy API default native retains current native/category-mode/feed behavior and rejects LLM as before. Production mode delegates to the actual top-level extract and enables source category capture through an explicit opt-in extraction setting propagated into the existing API and Unified/CSS source parsers. It binds the resulting original raw rows using existing category observer/normalizer/binder; it does not create another fallback algorithm. Validate explicit platform/shop scope before requests. Missing category capture is review-needed. Existing include_categories/category_mode endpoint semantics remain available in native mode.
- NC-FR2: Extraction-backed CLI operations categories extract, compare, analyze, catalogs, position, gaps, snapshot and watch expose the existing execution_options and policy_options controls instead of hardcoding ExecutionPolicy(). Existing browser-off/no-inference defaults remain. Categories extract chooses source_mode production by default at CLI level and offers explicit native compatibility mode. --browser enables existing browser fallbacks; --allow-llm opts into existing bounded provider configuration only for production mode. Native mode rejects incompatible LLM options before network. Reuse standard timeout validation, key redaction and provider budgets; avoid duplicate decorators or timeout options. File-only operations are unchanged.
- NC-FR3: Multi-site operations and watch create one shared execution state for the whole operation, not fresh LLM budgets for each URL/event. Existing concurrency and total operation timeout remain, existing status/errors/portable payloads remain compatible. Bounded model fallback never becomes source-supported category evidence merely because the model returned a label.
- NC-FR4: Browser configuration explicitly inherits the configured environment proxy without exposing credentials or falling back to direct routing when proxy parsing/configuration fails. Reuse the installed Crawl4AI BrowserConfig.proxy_config/ProxyConfig boundary for all shared browser configurations; HTTPX already inherits environment proxy. Prefer HTTPS_PROXY/https_proxy for HTTPS merchant work, otherwise ALL_PROXY/all_proxy then HTTP_PROXY/http_proxy where appropriate; malformed/unsupported configured proxy fails browser startup with redacted error. Do not unset proxy variables or mutate NO_PROXY/routes/allowlists. A single browser proxy may route more traffic through the proxy rather than bypass a network restriction; do not claim exact HTTPX NO_PROXY parity unless implemented/tested.
- NC-FR5: Audit records intentional source-specific feed/category-tree/HTTP-only tools limitations separately. Do not enable browser/LLM for bounded HTTP-only tools whose contracts/security explicitly exclude them, and do not change unrelated library defaults or install dependencies.

Scope order: sliceA core category capture/CLI controls and proxy preservation, then sliceB explicit production verifier. Independent review may approve sliceA separately; incomplete sliceB remains recorded.

## Narrow opt-in normalization repair

NC-FR6: Forward the existing restore_short_gtin boolean into _normalize_batch for UnifiedCrawl, CSS, LLM and terminal fallback branches, consistently with the API branch. Default false, source support checks and checksum validation remain unchanged; no new GTIN acceptance rule or normalization algorithm is introduced. Only an explicitly enabled, checksum-valid Shopify source barcode can be restored.

## Production platform detection amendment (pending independent review)

FP-FR8: Version2 sites may declare platform auto. The worker then delegates platform=None to the actual native extract detector and returns the observed result.platform. Existing explicit platforms remain supported; v1 does not accept auto. Auto profiles require unscoped reviewed mapping rules (explicit scoped mappings require an explicit platform); validate rule/target semantics before launch using the existing generic preflight scope, then normalize/map using the worker's actual returned platform and approved shop URL. Never guess a merchant platform from its domain. No detected platform is asserted for policy-skipped sources.

FP-FR8 invariant: the returned platform must be a real Platform value and must equal an explicitly declared profile platform; only auto permits a detected value to differ. Reject mismatch before normalization/mapping.
