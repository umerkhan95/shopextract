# Cold-checkout delivery amendment candidate

Observed delivery blocker: test.yml installs `-e .[dev,mcp]` before ignored taxonomy preparation, and publish.yml builds a cold checkout directly. The correctly fail-closed Hatch hook rejects both. Runtime/codec/catalog behavior is unchanged; fix delivery ordering before PR/merge.

## Chosen smallest shared path
Add ONE local composite action `.github/actions/prepare-taxonomy/action.yml`, used before project installation in tests and before package build in publishing. It installs existing declared Hatch tooling, then invokes ONE `scripts/bootstrap_taxonomy.py`. The standalone script reads pyproject metadata with stdlib tomllib (3.11+) or existing Hatch-declared tomli (3.10), and installs ONLY the exact existing HTTPX requirement selected from project.dependencies plus taxonomy-build (PyYAML). The HTTPX version constraint is not copied into another extra/list: these are the only external libraries used by the existing downloader/importer. No hardcoded dependency lists in scripts/workflows and no heavyweight application dependency bootstrap.

The entry point constructs a build-only package namespace `_shopextract_taxonomy_build` whose `__path__` is the trusted existing taxonomy module directory, then imports the SAME `.prepare` module and calls its CLI. Relative build/resource/validation/publish/download/contracts imports resolve to their unchanged existing files. It never executes shopextract/__init__.py or shopify/__init__.py, imports normalization/API modules, copies a builder, adds a generic import framework or changes runtime package imports. The namespace is process-local to explicit preparation; serialized artifacts contain ordinary unchanged primitive metadata, not Python class identities. Functions: `build_requirements(pyproject)->tuple[str,...]`, `load_preparer(root)->module`, `main(argv=None)->None`. One process performs preparation after dependency installation; no app parent memory duplication.

Both workflows explicitly select `--allow-download` in this CI/release-only action. Ordinary installed lookup, pip wheel/sdist installation and the Hatch hook remain offline; no automatic runtime/build-hook download. Local bootstrap accepts verified `--source-cache` and offline pip/no-download selection for tests. Preparation still pins release/commit/source hashes, downloads only existing allowlisted sources under existing limits, writes ignored build/, and relies on unchanged atomic publisher and force-includes for wheel+sdist. A local source override never silently falls back to network. The same action is the common preparation step; job-specific dev/MCP or build-tool installation stays in its existing workflow after/beside it.

Proposed changed files/SRP: bootstrap script owns checkout dependency/preparation sequencing only; composite action owns shared CI invocation/explicit network opt-in/thread environment; test.yml and publish.yml only invoke the common step in the correct order; focused delivery tests verify cold behavior and build-only metadata dependency selection; spec/test/status record actual evidence. No runtime source, pin, resource format, backend or safety policy edits.
