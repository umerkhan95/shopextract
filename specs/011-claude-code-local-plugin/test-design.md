## State and compatibility contracts
Each invocation progresses preflight -> submitted -> pending/terminal -> evidence/report or explicit early stop. Six-domain-call success path: discover, job_result(urls), extract, job_status, job_result(products), evidence. `job_result` may be unfinished: stop early rather than add polling. The status call is a bounded poll, not a completion guarantee. Use one chosen candidate URL, extract max_items=2, report at most two returned records and one retained evidence record. Calls after a budget/deadline stop are forbidden. Schema-only host ToolSearch/definition loading is excluded from the six-domain-call budget and recorded separately; failed or successful ShopExtract domain invocations still count. All host/schema activity, including preflight, shares the120-second wall deadline. This exclusion does not authorize other host tools or hidden domain execution. Fixtures may await real completion without calling an extra tool to obtain deterministic mechanism evidence; this does not prove model behavior.

Source fixture seed 24 is deterministic, no random sweep. Extend only the controlled outbound boundary; never fake runtime extraction/jobs/evidence. Distinct cases cover syntax, launch boundary, source policy, normalization/support fidelity, asynchronous early stop, lifecycle and model activation. Existing server limits remain authoritative. A safety inventory check must not be described as the native host rejecting files it accepts.

### Concrete revised boundaries and expected test corpus

Discovery max_items2 and operator source limits stay unchanged. Candidate selection operates only on returned URLs. Whole path segments are decoded/case-insensitive for exclusion/markers; exclude blog/article/news/journal segments before considering positive product markers. Preference order: products, product, p, item, dp; require another nonempty path segment; lexical original URL tie-break. Positive selection must remain same authorized origin; no rewritten/guessed extraction target. A query-only product ID or unknown route yields exact no-product stop. At most12 small selection vectors cover each distinct classification risk; this is not random variation or a broad sweep.

The realistic source fixture has a2-entry sitemap index and2entry maps: a blog-first case makes one visible blog URL then one product URL; a no-product-boundary case makes two blogs before an unseen product. A same-origin product redirect succeeds through existing guard, while a denied cross-origin/private redirect has no target request and explicit failure. Source request ceiling remains existing configured maximum (fixture target<=8requests); extractionmax2; fixture bytes<=16KiB per document. Finite external delays are <=1second and cleanup<=2seconds; direct asynchronous cases<=15seconds, SDK process cases<=20seconds. No domain reports/job engine/parsers are mocked. Existing indefinitely held fixture gates need not be expanded for this follow-up; representative finite delays are additional coverage.

The old `after_submit` successful SDK trace stays labeled **synchronized mechanism-only**. Revised unsynchronized tests prove honest early pending. No model-side sleep/wait capability or shell command is introduced. A discovery-ready/extraction-pending case may coordinate at the external request-start boundary to establish phase ordering, but must not await job completion after submission before testing status. Any optional offline-only synchronization is explicitly visible in trace provenance.

### Revision G2 bound/wiring clarification (2026-10-25)

Concrete native harness limits: **max-turns10**, **wall deadline120seconds**, then at most **2seconds cleanup total** (owned process group TERM/wait<=1second, then KILL/reap<=1second). Each case still has <=6domain calls/<=2products and separately counted schema calls. Turn count is a second inference bound, not a replacement for domain/wall enforcement. No arbitrary host sleep or extra model retry. Use only an owned new process group; never signal an existing user client/group. If reliable group cleanup is unsupported on a platform, native execution is blocked rather than claiming cleanup. A controlled non-model supervisor test uses wall.2s plus cleanup2s, with <=1s scheduling allowance in elapsed assertion; the allowance does not extend the production120s wall.

The opt-in host preflight must gather and save actual selected-client identity/auth and required flag support, including finite `--max-turns 10`, before any inference. A version/help string alone is insufficient. A non-inference argument-acceptance probe and known compatible version/capability evidence must support the bounded invocation; missing/ambiguous capability blocks. ### Supplemental SC15b: normal host exit with live owned descendant (design for review)

Risk: the current supervisor only calls cleanup when its direct parent is still running or an error occurred. A successful CLI can exit0 while an owned MCP descendant closes/redirects its stdout/stderr and remains alive; pipe EOF/direct wait alone cannot prove group cleanup. This is distinct from timeout of a TERM-ignoring direct child.

Proposed acceptance: a controlled Python parent creates one child in its newly owned session/group, records child PID/group and exits0 after the child's bounded ready marker; child redirects stdio and waits at most30s, ignoring TERM. Supervisor must always inspect/clean its owned group after normal completion too, preserve parent returncode0, and terminate the remaining child within the same2s cleanup budget. No shell or external/model/native client. Outer test deadline5s and fallback signal only after verifying the child's still-owned group/session; never signal a reused PID/group. Assert no **running** child survives. A dead orphan zombie may be reaped by the OS ancestor rather than this supervisor; do not claim direct-child reaping for indirect descendants or a stronger guarantee than observed. Record cleanup limitation if group disappearance cannot be verified. Production code changes wait for independent review of this supplemental case.

Supplemental existing FR14 permission boundary: a host-level unenveloped tool_result permission error must be classified `host_tool_permission_denied` and cannot satisfy completed evidence. The harness must not auto-approve/bypass the rejection; this is distinct from a real domain permission_denied envelope used for a prerequisite outcome.
