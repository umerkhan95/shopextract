# Open taxonomy compatibility evaluation

## Outcomes and requirements
FR01: evaluate reusable official open category/attribute data before proposing bespoke category policies. Pin Shopify release2026-08, commit2e9aa2e9b882383952c63d212add13eb80f46cf9; verify source license. FR02: test a laptop, boot/footwear and refrigerator category against real existing category capture/mapper/companion and compare/profile paths. FR03: retain exact upstream IDs/attributes/provenance; never imply downloaded category definitions authorize correction, prove source assignment, or supply missing RAM/size safety rules. FR04: expose registry/config bounds and policy gaps rather than silently importing everything.

## Boundaries
Research/compatibility experiment only; no production importer, policy additions, library dependency/install, model, provider, storefront request, Git publication or change to completed006. Saved upstream data is actual downloaded reference data; product fixtures are derived synthetic offline. No automatic classification from product titles.

## Acceptance
SC01: exact upstream Laptops category is unique, has ID/nonempty attributes. SC02: actual captured synthetic assignments map only via explicit exact trusted rules into pinned target IDs, source version remains honestly unknown where adapters omit it. SC03: attributes resolve to upstream definitions; distinguish standard display names/enum values from maintenance FieldRule roles/unit normalization. SC04: mutation of native category ID or absent assignment cannot become mapped; hierarchy/sibling and explicit profile safeguards unchanged. SC05:1001 distinct actual source category IDs rejected by existing1000-target validator; relevant subset succeeds. SC06: separate supported coverage from missing capabilities and preserve byte/source/runtime evidence.
